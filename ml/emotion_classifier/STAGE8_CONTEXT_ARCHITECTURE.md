# Stage 8 Context Architecture

The active emotional check-in path is Node `adaptiveChatController` → `narrativeAnalysisService` → `emotionPredictionService` → FastAPI `backend/ml/emotion_classifier/api_service.py` at `http://localhost:8001/predict-emotion`. The API loads v4 by default from `model_runtime.py`; `EMOTION_MODEL_VERSION=tfidf_linear_svm_calibrated_v3` selects rollback. Node retains its rule fallback. Contextual question selection/result aggregation remains in the existing adaptive services; the five-turn session contract and caregiver alert flow were not changed.

The service currently receives an answer string from the adaptive controller. After that answer-only prediction, Node uses the current question and prior interpreted state in its rule-based contextual answer interpretation. The FastAPI schema accepts optional request-scoped context, but all available models are answer-only and deliberately ignore it. They report `context_aware: false`. No live supervised conversation dataset or validated contextual model exists. `context_dataset_schema.py` validates future human-labelled records; `context_builder.py` supports `answer_only`, `question_answer`, and `multi_turn` formats. `format_model_inputs` enforces declared model metadata and refuses missing/cross-owner context for future contextual use. The contextual registry entry has no artifact and cannot be selected.

Emotion inference has its own lazy auto-start manager in `backend/src/services/emotionMlServiceManager.js`; it validates service identity, readiness, active model, artifact integrity, and classes before sending a prediction. The generic `mlServiceManager.js` serves other endpoints and expects `ml-service` at the repository root (or `ML_SERVICE_DIRECTORY`). That directory is absent in this checkout, so generic startup reports the missing service and does not mistake the emotion API for a generic predictor. The generic service needs its own package and port.
